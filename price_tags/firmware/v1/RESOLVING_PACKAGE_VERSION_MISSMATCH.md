# Resolving package version mismatches

Run these commands from `price_tags/firmware/v1`.
Dependencies and features belong in `Cargo.toml`; target, linker, and
`build-std` settings belong in `.cargo/config.toml`.

## The conflict fixed here

`esp-radio 0.18.0` and `esp-rtos 0.3.0` require `esp-hal ~1.1.0-rc.0`.
`esp-storage 0.10.0` requires `esp-hal ~1.2.0-rc.0`. These requirements do
not overlap. Making storage optional does not eliminate the conflict:
Cargo resolves optional dependencies into the lockfile too.

Keep the related ESP crates in a compatible release family rather than
independently choosing the newest version of each crate:

| Crate | Compatible manifest requirement |
| --- | --- |
| `esp-hal` | `1.1.1` (currently locks to `1.1.2`) |
| `esp-radio` | `0.18.0` |
| `esp-rtos` | `0.3.0` |
| `esp-alloc` | `0.10.0` |
| `esp-sync` | `0.2.1` |
| `esp-backtrace` | `0.19.0` |
| `esp-println` | `0.17.0` |
| `esp-metadata-generated` | `0.4.0` |
| `esp-bootloader-esp-idf` | `0.5.0` |
| `esp-storage` | `0.9.0` |

These are Cargo version requirements, not exact pins. For example, `"1.1.1"`
means `^1.1.1`, which permits later compatible 1.x releases. The radio/runtime
requirements constrain the resolved HAL to 1.1.x. Pre-1.0 minor versions are
separate compatibility ranges: `"0.9.0"` does not permit `0.10.0`.
Keep `Cargo.lock` to preserve the versions actually verified.

## Efficient troubleshooting workflow

1. Reproduce the exact failing build before changing versions:

   ```sh
   cargo build --bin esp32s3 --features esp32s3
   ```

2. Read both sides of Cargo's conflict. Identify the shared dependency and
   which parent crate imposes each range. Inspect those parents directly:

   ```sh
   cargo info esp-radio@0.18.0 --verbose
   cargo info esp-rtos@0.3.0 --verbose
   cargo info esp-storage@0.9.0 --verbose
   ```

   Use the dependency requirements and feature lists, not just the crate's
   headline version. If resolution already fails, `cargo info` is more useful
   than `cargo tree`, which needs a resolvable graph.

3. Change the smallest coherent family in `Cargo.toml`. If upgrading the HAL
   to a new release family, first verify matching radio, runtime, storage,
   allocator, and diagnostics releases exist. A lockfile pin cannot satisfy
   disjoint manifest requirements, and deleting the lockfile or running
   `cargo clean` does not fix them.

4. Resolve by building again. Once the graph resolves, inspect dependency
   parents, enabled features, and duplicates:

   ```sh
   cargo tree --target xtensa-esp32s3-none-elf --features esp32s3 -i esp-hal
   cargo tree --target xtensa-esp32s3-none-elf --features esp32s3 -e features
   cargo tree --target xtensa-esp32s3-none-elf --features esp32s3 -d
   ```

   Multiple versions are not automatically bugs. They matter when types cross
   version boundaries, a crate's `links` value must be unique, or multiple
   runtimes/global allocators are linked. Do not force unrelated dependencies
   to one version just to remove duplicate entries.

5. For a targeted lockfile adjustment within existing requirements, use:

   ```sh
   cargo update -p esp-hal --precise 1.1.2
   ```

   Review changes to both manifests and the lockfile. Avoid a broad
   `cargo update` unless updating the entire graph is intentional.

## Features, platform isolation, and linking

All direct ESP dependencies and the backend's networking/executor dependencies
are optional and scoped to bare-metal Xtensa/RISC-V targets. `default = []`
keeps the portable `no_std` SD-card library independent of ESP.
The binary's `required-features` prevents default builds from selecting it.
Select exactly one chip; `--all-features` enables incompatible chips.

Each chip feature forwards its selection to the ESP dependencies.
`esp-storage?/esp32s3` forwards the chip only when storage is enabled; it does
not turn storage on. Test storage explicitly when changing its version:

```sh
cargo build --bin esp32s3 --features esp32s3,esp-storage --locked
```

Successful dependency resolution is not sufficient for a firmware build:
`esp-backtrace` needs its panic-handler/output features, `esp-println` supplies
the defmt logger, and RTOS startup needs both a timer and software interrupt.
The ESP32-S3 configuration uses the Espressif GNU linker with `-nostartfiles`,
`linkall.x`, and `defmt.x`. Do not apply those flags globally to other targets.
`rust-lld` failed with the Xtensa linker scripts in the tested toolchain.

The local `rust-toolchain.toml` selects `esp`, installed with `espup`.
Load the environment generated by `espup` so `xtensa-esp32s3-elf-gcc` is on
`PATH`. Missing tools/targets are environment problems, not package conflicts.

## Verify both firmware and portability

```sh
cargo build --bin esp32s3 --features esp32s3
cargo +stable build --no-default-features --target x86_64-unknown-linux-gnu --locked
cargo +stable check --lib --features esp32s3 --target x86_64-unknown-linux-gnu --locked
cargo +stable tree --no-default-features --target x86_64-unknown-linux-gnu --depth 1
```

Use an installed host target instead of `x86_64-unknown-linux-gnu` on other
systems. The host tree must not include direct ESP dependencies. For another
installed MCU target, also check the library with `--lib --no-default-features
--target <target>` using a suitable toolchain. The portable library was also
checked on `thumbv7em-none-eabi`.

After the initial successful build, repeat it with `--locked` in CI to prevent
unintended lockfile changes. A linked ELF is not a hardware test: Wi-Fi,
DHCP, HTTP, and storage behavior still need validation on a board.
